# גיבוי ושחזור

> מה מגובה, מה **לא**, ומה בדיוק עושים ביום שצריך לשחזר.
>
> נכתב 8.9.2026 מול פרויקט `shcauvnepnaemmnvahgy` (Postgres 17.6, אזור
> `eu-central-1`). סוגר את `G-014`.
>
> ⚠️ **נוהל השחזור שלמטה מעולם לא תורגל.** זה נאמר בראש המסמך ולא בסופו, כי
> נוהל שחזור שלא הורץ הוא הבטחה ולא יכולת. התרגול חסום על ארגון חי עם נתונים —
> ראה "התרגול" בסוף.

## 1 · מה מגובה, ומי מגבה אותו

| מה                                              | איפה זה יושב            | מי מגבה                       |
| ----------------------------------------------- | ----------------------- | ----------------------------- |
| כל 193 הטבלאות של המוצר                         | `public` בפוסטגרס       | סופאבייס                      |
| המשתמשים והסשנים                                | סכימת `auth`, אותו מסד  | סופאבייס, באותו גיבוי         |
| הרשאות, RLS, פונקציות, טריגרים                  | הסכימה עצמה             | סופאבייס, באותו גיבוי         |
| **תמונות הנכסים**                               | `storage.objects` + S3  | **לא בגיבוי המסד** — ראה למטה |
| הקוד, המיגרציות, מרשם הפערים                    | git · GitHub            | GitHub + כל שיבוט מקומי       |
| הסודות (`SWEEP_RELEASE_SECRET`, `DATABASE_URL`) | משתני סביבה בספק הפריסה | **אף אחד** — ראה למטה         |

### שני הדברים שאינם מגובים, ושהיו נעלמים בשקט

**התמונות.** דלי `property-photos` (0076) הוא אחסון אובייקטים ולא שורות במסד.
שחזור המסד לנקודת זמן מחזיר את השורות שמצביעות על התמונות ולא את התמונות עצמן;
התוצאה היא נכסים עם קישורים שבורים, שנראים על המסך כמו "התמונה לא נטענה" ולא
כמו אובדן נתונים. **צריך גיבוי נפרד לדלי.**

**הסודות.** הם רק במשתני הסביבה של ספק הפריסה. אם החשבון נסגר או המשתנה נמחק —
הסוללות מפסיקות לעבוד ואין מאיפה לשחזר את הערך. שמור עותק במנהל סיסמאות.

## 2 · לפני שצריך — שלושה דברים לוודא פעם אחת

1. **באיזו רמת גיבוי הפרויקט נמצא.** לוח הבקרה של סופאבייס → Database → Backups.
   התוכניות נבדלות בין גיבוי יומי לבין Point-in-Time Recovery, וההבדל הוא בין
   "אבדנו עד יממה" ל"אבדנו דקות". **בדוק את זה עכשיו ולא ביום האירוע** — זו
   ההחלטה היחידה כאן שמשפיעה על כמה נתונים נאבדים, והיא מתקבלת מראש.
2. **הורדה אחת ידנית, לאחסון שאינו סופאבייס.** גיבוי שנמצא רק אצל הספק שנפל
   אינו גיבוי:
   ```bash
   pg_dump "$DATABASE_URL" --no-owner --format=custom --file=estia-$(date +%F).dump
   ```
   הקובץ מכיל **פרטי אורחים** — שמות, טלפונים, מסמכים. הוא כפוף לאותה מדיניות
   פרטיות כמו המסד עצמו (ראה `PERSONAL_DATA_INVENTORY.md`). מוצפן, ולא בדוא״ל.
3. **עותק של דלי התמונות:**
   ```bash
   supabase storage download --recursive property-photos ./backup-photos
   ```

## 3 · שחזור — לפי מה שקרה

### א · שורה אחת נמחקה בטעות

**אל תשחזר את המסד.** רוב הישויות במוצר משתמשות במחיקה רכה (`deleted_at`), ורוב
מה שנראה כמחיקה הוא שינוי סטטוס. בדוק קודם:

```sql
select id, deleted_at from public.<table> where id = '<uuid>';
```

יש `deleted_at`? זו החזרה של שדה אחד, ולא אירוע. יש גם `public.audit_events` —
מי עשה מה ומתי, כולל ה-`before` של השינוי. **התחל שם.**

### ב · טבלה או סכימה נפגעו ממיגרציה שנכשלה באמצע

זה התרחיש ש-`G-026` מתאר. בלי `DATABASE_URL` המיגרציה מוחלת משפט־אחר־משפט ואין
`ROLLBACK`.

1. **אל תריץ שוב את אותה מיגרציה.** היא תיכשל על מה שכן נוצר.
2. קרא את הקובץ ומצא איפה זה עצר — כל מיגרציה במאגר הזה בנויה
   `create ... if not exists`, כך שהחלה חוזרת של החלק הראשון בטוחה.
3. אם החלק שנכשל אינו idempotent — כתוב מיגרציה חדשה שמתקנת. **מיגרציה שכבר
   הוחלה אינה נערכת** — זה הכלל שכל המאגר מציית לו.
4. **הגדר `DATABASE_URL` כדי שזה לא יקרה שוב.**

### ג · אובדן נתונים אמיתי — שחזור לנקודת זמן

```
לוח הבקרה → Database → Backups → Restore
```

**סדר הפעולות, ולמה בסדר הזה:**

1. **הורד את האפליקציה תחילה.** שחזור בזמן שבקשות כותבות יוצר נתונים שהשחזור
   לא כולל ואי אפשר לאחות אותם אחר כך.
2. בחר נקודת זמן **לפני** האירוע, לא בזמנו.
3. השחזור מחליף את המסד כולו — כולל `auth.users`. משתמש שנרשם אחרי אותה נקודה
   **ייעלם**, והסשן שלו יישבר בלי הסבר.
4. אחרי השחזור, שחזר את דלי התמונות **בנפרד** מהעותק שלך.
5. הרץ את בדיקות הבידוד לפני שמחזירים תנועה:
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/isolation.sql
   ```
6. ודא שהסכימה במקום שאתה חושב:
   ```sql
   select count(*) from supabase_migrations.schema_migrations;
   ```
   מול מספר הקבצים ב-`supabase/migrations/`. שחזור לנקודה ישנה **מחזיר גם את
   הסכימה אחורה**, והקוד הפרוס מצפה לחדשה. אם המספרים לא תואמים — הפעל את
   המיגרציות החסרות לפי הסדר לפני שמחזירים תנועה.

### ד · הפרויקט כולו אבד

1. פרויקט סופאבייס חדש, **באותו אזור** (`eu-central-1` — פרטי אורחים ישראליים
   מחוץ לאיחוד האירופי הם שאלה משפטית ולא טכנית).
2. `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f <file>` לכל מיגרציה לפי הסדר, או
   `supabase db push`.
3. `pg_restore` מה-dump.
4. שחזור הדלי.
5. **עדכן `NEXT_PUBLIC_SUPABASE_URL` ואת המפתחות, ופרוס מחדש** — הם נצרבים
   ל-bundle בזמן build ולא נקראים בזמן ריצה.

## 4 · התרגול — מה שנשאר פתוח, ולמי

הנוהל למעלה נגזר מקריאת הסכימה והקוד. **הוא לא הורץ.** מה שתרגול היה מגלה, ומה
שקריאה לא יכולה:

- כמה זמן לוקח שחזור בפועל, וכמה זמן העסק למטה.
- האם `pg_restore` על מסד עם RLS **נכפה** על 193 טבלאות עובר נקי.
- האם הקישורים לתמונות מתאחים אחרי שחזור הדלי בנפרד.

התרגול דורש ארגון חי עם נתונים (`G-023`), ולכן הוא חסום על אותו דבר שחוסם את
בדיקת המסע מקצה לקצה. **הרגע הנכון: אחרי הלקוח הראשון, לפני השני.** לתרגל על
נתוני הלקוח הראשון זו הדרך היחידה לדעת שיש מה להבטיח לשני.
