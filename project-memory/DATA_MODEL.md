## 1. העיקרון שמכתיב את כל השאר

> **הארכיטקטורה המלאה מהיום הראשון. המימוש לפי סדר.**

יש דברים שאפשר להוסיף מתי שרוצים, ויש דברים שאם לא נכנסו במיגרציה הראשונה
— התיקון בדיעבד הוא פרויקט של חודשים.

**מה שנכנס עכשיו, גם עם לקוח אחד:**

| מה                                      | למה לא אחר כך                                 |
| --------------------------------------- | --------------------------------------------- |
| `organization_id` על כל ישות            | להוסיף על נתונים כספיים חיים = מיגרציה מפחידה |
| `User → Membership → Organization`      | לשנות אחר כך = לגעת בכל נתיב הרשאה במערכת     |
| `created_by` · `updated_by` · `version` | להוסיף אחר כך = לעבור על כל נתיב כתיבה        |
| Soft delete                             | נתונים שנמחקו קשה = אבודים                    |
| Audit על פעולות רגישות                  | אין דרך לתעד למפרע                            |
| Idempotency בתשלומים                    | מתגלה כשמישהו חויב פעמיים                     |
| Guest כישות נפרדת מ-User                | ערבוב = חוב אבטחה קבוע                        |
| RLS על כל טבלה מרגע יצירתה              | טבלה בלי חוק היא דלת פתוחה                    |
| Scope על Membership                     | להוסיף אחר כך = כל דוח וכל ייצוא נבדקים מחדש  |
| `brand` כשכבה אופציונלית                | היררכיה חדשה על נתונים קיימים = כאב           |

**עמודה שאפשר להתעלם ממנה עולה כלום. היררכיה שמוסיפים אחרי אלף נכסים
עולה חודשים.**

## 3. הזהות — הלב

```
┌──────────┐         ┌──────────────┐         ┌───────────────┐
│  users   │◄────────┤ memberships  ├────────►│ organizations │
└──────────┘  1    n └──────┬───────┘ n     1 └───────────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
     ┌────────────────┐ ┌────────────┐ ┌──────────────────┐
     │membership_roles│ │  scopes    │ │  preferences     │
     └───────┬────────┘ └────────────┘ └──────────────────┘
             │ n                          שפה · התראות
             ▼ 1
        ┌─────────┐  n      n  ┌──────────────┐
        │  roles  ├───────────►│ permissions  │
        └─────────┘            └──────────────┘
              role_permissions

   ┌────────┐   נפרד לחלוטין. אין חשבון, אין חברות, אין תפקיד
   │ guests │   גישה דרך קישור מאובטח להזמנה אחת בלבד
   └────────┘
```

**הכלל:** `User → Membership → Organization → Roles → Permissions → Scope`.

**לעולם לא `user.organization_id`.** אותו אדם יכול להיות מנהל בארגון א׳,
בעל נכס בארגון ב׳ ורואה חשבון בארגון ג׳ — עם זהות אחת, סיסמה אחת ו-MFA אחד.
במודל שבו משתמש שייך לארגון זה בלתי אפשרי.

### מה `membership` מחזיק

`user_id` · `organization_id` · `status` · `joined_at` · `invited_by` ·
`last_active_at` · `default_property_id` · `employment_type` · `team_id` ·
`language` · `notification_preferences`

**סטטוסים:** `invited` · `pending` · `active` · `suspended` · `removed`

**הסרת עובד אינה מחיקה.** הסטטוס עובר ל-`removed`, הגישה נסגרת מיידית,
וכל מה שהוא עשה נשאר מתועד בשמו. עובד שנמחק מהמסד הופך שנתיים של Audit
לבלתי קריא.

### למה `guests` נפרדת

אורחים רבים בסדרי גודל מעובדים, אינם מאומתים, ודורשים משטר גישה **הפוך**:
עובד מתחבר ומקבל טווח רחב לאורך זמן; אורח מקבל חלון צר לרשומה אחת, לזמן
מוגבל. ערבוב השניים הוא חוב אבטחה שלא מתקנים.

## 6. המטא-דאטה שכל רשומה נושאת

```sql
organization_id  uuid        not null   references organizations(id)
created_at       timestamptz not null   default now()
created_by       uuid                   references users(id)
updated_at       timestamptz not null   default now()
updated_by       uuid                   references users(id)
version          integer     not null   default 1
```

ובמקום המתאים:

```sql
deleted_at       timestamptz
deleted_by       uuid                   references users(id)
```

### `version` — נעילה אופטימית

זה מה שמונע דריסה בין משתמשים.

> שי פותח טופס הזמנה. רוני משנה את המחיר ושומרת — `version` עולה מ-4 ל-5.
> שי לוחץ שמור עם `version = 4`. **השמירה נדחית עם הסבר**, במקום למחוק
> בשקט את השינוי של רוני.

הכתיבה תמיד:

```sql
UPDATE bookings SET ..., version = version + 1
WHERE id = $1 AND version = $2 AND organization_id = $3
```

אפס שורות מושפעות = מישהו הקדים אותך.

**זו עמודה שמוסיפים בהתחלה או לא מוסיפים לעולם.** להוסיף אותה אחרי שנתיים
פירושו לעבור על כל נתיב כתיבה במערכת.

### מחיקה רכה

`deleted_at` במקום `DELETE`. הרשומה נעלמת מהתצוגה ונשארת בנתונים —
כי "מחקתי בטעות את ההזמנה" היא שיחת תמיכה שקורית, ו"נתון שנמחק קשה"
היא שיחה שאין לה סוף טוב.

## 7. Audit

```
audit_events
  id · organization_id · actor_type · actor_id · property_id
  resource_type · resource_id · action
  before (jsonb) · after (jsonb)
  occurred_at · ip · device · request_id
```

`actor_type` מבחין בין `user` · `system` · `ai` · `platform_staff`.
**ה-AI הוא סוג שחקן מבוקר** — הוא כותב תוכן שמופיע מול לקוחות ומציע
מחירים, ובלי מעמד ב-Audit השאלה "מי כתב את זה" נשארת בלי תשובה.

**append-only.** אין `UPDATE` ואין `DELETE`, גם לא לבעלים.

הרישום אומר **מה קרה**, לא **שמשהו קרה**:

> ✅ שי שינה מחיר הזמנה מ-₪5,200 ל-₪4,700
> ❌ Booking updated

## 8. Idempotency

תשלום, החזר, חשבונית, יצירת הזמנה, webhook והתראה מחזיקים מפתח ייחודי
לכל פעולה, עם אילוץ `UNIQUE` במסד.

ניסיון חוזר — רשת שנפלה, לחיצה כפולה, webhook שהגיע פעמיים — **לא יכול**
לחייב פעמיים · להפיק שתי חשבוניות · ליצור שתי הזמנות · לשלוח פעמיים קוד דלת.

**זה נבנה לתוך הטבלה מהרגע הראשון, לא כתיקון אחרי התקרית.**

## 10. חוקי סכימה שאין מהם חריגה

1. **כל טבלה עסקית נושאת `organization_id`**, ומקבלת חוק RLS
   `organization_id IN my_organizations()` **ברגע יצירתה**.
2. **אין `tenant_id`, אין `business_id`, אין `company_id`.**
3. **כסף = `integer` באגורות.** לעולם לא `float`, לעולם לא `numeric`.
4. **תאריך ושעה = `timestamptz`.** לעולם לא `timestamp` בלי אזור זמן —
   ישראל מחליפה שעון פעמיים בשנה.
5. **אינדקס על כל מפתח זר**, ועל כל עמודה שמסננים לפיה בפועל.
   `organization_id` ראשון בכל אינדקס מורכב.
6. **אילוץ ייחודיות במסד**, לא בקוד. מספר חשבונית, מפתח idempotency,
   וחפיפת הזמנות על אותה יחידה.
7. **מיגרציה היא קובץ בגרסה.** שינוי שנעשה בקונסולה ולא בקובץ — לא קיים.
8. **שינוי הרסני עובר מסלול:** להוסיף → למלא → להעביר קוראים → ורק אז
   להסיר.
